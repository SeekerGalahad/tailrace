## 一、④ group commit 吞吐档 —— 结论：**维持排 v1.x/R6（未触发），但判据状态实质更新**

T18 预设三触发器（纪要 :63）逐条检验：

### ④T1「先立 Doris sink 宏基准小卡」—— ✅ 已满足（无争议）

T32 交付（cb825f6）：单管大批/单管小批/P=4 并发×2 档/starrocks 六档，行数守恒全过，
§6.4 含口径注记与复现命令（:686-696）。T18 共同事实 4（「④ 无门槛数据可依」）就此关闭。

### ④T2「默认档吞吐不达标**且**瓶颈在 FE 事务/BE compaction 队列而非网络/CPU」—— 半成立：**瓶颈归因成立（小批域）；「默认档不达标」被同一数据否定**

两个子句分判（数据 §6.4，全部同机同日 debug 档、100k 行、行数守恒）：

- **「瓶颈在 FE 事务（提交频率）而非网络/CPU」——成立**，证据链（排除法+往返记账）：
  1. **大批域 sink 零开销**：doris 单管大批 33852 vs file→file 33568 = **+0.8%，噪声界内持平**
     （§6.4 :653-655）——10k 行批的 stream load 不在热路径上，网络带宽与全链 CPU 均非约束；
  2. **小批域耗时被同步往返完全记账**：单管小批 elapsed 9.077s / 200 次 flush = **45.4ms/次**
     同步 stream load 往返（§6.4 :661-662 自记 ≈45ms）——200×45.4ms≈9.08s≈elapsed，
     吞吐被「每 flush 一次 FE 事务（label 建 txn→commit）的串行往返次数」封顶（−67% vs 大批）。
     非网络：localhost compose 网、500 行≈47KB 载荷（~95B/行，§6.4 :631），传输亚毫秒级，
     45ms 为服务端处理；非引擎 CPU：transform 微基准 237M/65.9M/53.5M rows/s（§6.5 :711-713）
     高出三个数量级，且 P=4 poll 地板批 97752=单管大批 2.89×（§6.4 :666-667）证明单管道时
     CPU/全链大量闲置；非 BE 写路径/compaction 退潮：P=4 小批 4 路并发 2.43× 重叠无降级
     （:662-663）、poll 地板批 97752 持续吸收（:667-668「单机 BE 2.1.7 可吸收 4 路并发
     stream load 无退潮」）。
  3. **归因方式的诚实边界**：45ms 往返是整体测量，拆到 FE 事务协调（label 校验/txn 建/
     commit）靠排除法+记账收敛；**未采集 FE audit log/compaction 队列指标**（T32 范围外）。
     「BE compaction 队列」半句无正面证据也无反证——观测到的约束是提交频率，不是后台合并。
- **「默认档吞吐不达标」——不成立**：默认攒批档（flushRows 10000）恰是 +0.8% 持平的那一档
  （§6.4 :642）。默认档没有病，病的是小批配置域——而那正是 group commit 的官方收益区
  （T18 §④ :61 场景错配疑点的数据面证实）。

**判定**：T2 的意图（为 group commit 圈定收益区并证明瓶颈位置）已达成；T2 的字面前半句
（默认档不达标）被数据否定。合读=**group commit 的收益区=小批高并发写入域，且该域瓶颈
确在每-flush FE 事务提交频率**——T32 自记同结论（§6.4 :663-665「并发有相对收益、无绝对
追平，收益缺口即 Doris group commit（或引擎侧攒批合并）的目标区」）。

### ④T3「真实出现多管道小批量场景（≥4 管道 × <1000 行批）」—— 机制面成立、需求面未触发

- **机制面**：P=4 × flushRows 500 = 26781 rows/s = 单管小批 11017 的 **2.43×**（§6.4 :644、
  :662）——并发确实部分重叠了 45ms 往返（串行 4×50×45.4ms≈9.08s 压缩到 3.734s），配置形态
  （≥4 管道 × <1000 行批）在基准里成立。
- **需求面**：T3 原文是「**真实出现**」——指真实部署场景，基准构造不构成真实需求。外部信号
  复测为零（§〇.1）；仓内亦无小批多管道的默认配置或文档化场景。**未触发**。
- 附加事实（R6 卡须带上）：即便 P=4 并发，26781 仍 **−21% vs 单管大批 33852**（§6.4 :663）
  ——并发追不平大批，缺口即 ④ 的目标区；且 T32 实证探小批必须同压 pollRows（批粒度地板
  =pollRows，:669-671），R6 卡的实验设计直接沿用。

### ④ 结论与续挂触发器

## 二、③ vs ⑤ 二选一（2PC 服务端裁决 vs WAL 客户端裁决）—— 结论：**双双维持排 v1.x（触发器均未发）；谱系卡预定分支=③ 2PC，附唯一翻转条件**

### 触发器检验（T18 ③T1 :53 / ⑤T1-T2 :74）

- **③T1（exactly-once 硬需求+实际损害案例）**：未触发——需求信号零（§〇.1），且零重复损害
  登记维持（T18 §〇/§③ :49：chaos kill-9 幂等对账 §5.1 `BENCHMARKS.md:333`、T11 S8
  1700==1700、T12 同 label 重放 Dedup 不双写；本轮无新损害案例入账）。
- **⑤T1（实测重复率>0 且下游不可消解）**：未触发——同上，防线实测全绿记录未被打破；
  T32/T33 均为吞吐数据，不产生正确性新证据。
- **⑤T2（③若触发，先做谱系裁决二选一）**：T36 即该裁决的正式召开（本节）。

### 裁决：若共同触发器发射，谱系卡**选定 ③ 2PC（服务端裁决）**，理由四条

1. **代价封闭性（决定性）**：2PC 只动 sink 协议面（conn-doris header + Sink trait
   prepare/commit/abort 默认实现=file/kafka 零改动，T18 :54 草案）；WAL 动引擎持久面，
   对**所有**管道课税——flush 点持久写次数翻倍（T18 :72），而宏基准链路本就 fsync 主导
   （§4.4 `BENCHMARKS.md:227/:444`「全链 debug 档由 decode 与 fsync 落盘主导」、§2.3 观察
   :71 fsync×2 使整 flush 比纯编码慢 ~41 倍），file sink flush 458.2K rows/s 基线（§4.1 :136）
   上可预期显著回吐，直接打击
   41528 锚点（§6.5）与 P=4 97752 天花板（§6.4）。
2. **损害模型对位**：共同触发器=「重复且造成实际损害」。第三支柱 sink（Doris/StarRocks）
   上 label 幂等已把崩窗重放收敛为 Dedup（lib.rs:496），WAL 的边际正确性收益≈0；2PC 补的
   恰是 label 补不了的另一半（abort/孤儿事务对账）。file/kafka（无幂等键）上 2PC 无作用
   ——但那正是下述翻转条件管辖的唯一场景。
3. **支柱对位**：③ 在北极星第三支柱谱系上（label 幂等→事务接口 exactly-once→group commit
   吞吐档，roadmap :15）；⑤ 是引擎通用件、谱系外。
4. **与 ④ 的交互**：若 ④ 的 async_mode group commit 将来被采纳（放弃 label 级确认，
   T18 :62），幂等锚弱化——服务端 2PC 是同一 sink 面上可配对的补强；WAL 救不回 async
   group commit 下的逐 load 确认。

### 翻转条件（唯一，写死）

若重复损害案例落在**无幂等键 sink（file append / kafka 投递）**而非 Doris/StarRocks——
2PC 无标的，谱系卡翻转选 ⑤ WAL（客户端裁决，估 ~3 人日，承 T18 :75 草案：意图条目格式/
assign-only 不动/恢复先对账/吞吐回吐量化入 BENCHMARKS/kill-between-flush-and-save 定点
chaos 测试）。两分支**不同时做**（T18 :74 原则维持——同一崩窗，一个裁决权在服务端一个在
客户端，选一即封窗）。

### ③⑤ 结论

- **③ StarRocks 事务接口（2PC）**：排 v1.x 维持；触发器=③T1 原文续挂（:53），触发后按本节
  预定分支直接进 2PC 卡（T18 :54 草案有效：Sink trait 三点默认实现/`two_phase_commit`
  header+PRECOMMITTED 状态机/孤儿事务对账/T12 allin1 复用/契约测试补事务面，估 ~3-4 人日）。
- **⑤ 本地两步 WAL**：排 v1.x 维持；触发器=⑤T1 原文续挂（:74）**且仅限翻转条件场景**——
  损害在幂等键 sink 上出现时才开卡；③ 触发而损害在 Doris/StarRocks 上时**不开** WAL 卡。
