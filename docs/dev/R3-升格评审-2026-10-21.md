## ④ group commit 吞吐档 —— 结论：排 v1.x，且升格前必须先补 Doris sink 宏基准（当前无门槛数据可依）

- **现状证据**：grep `group_commit` conn-doris/全仓代码 **0 命中**；上游 Doris ≥2.1 支持（compose 2.1.7 栈即支持，共同事实 3）。
- **门槛数据**：
  - **直接前置缺口**：BENCHMARKS 无任何 Doris/StarRocks sink 吞吐行（共同事实 4）——「吞吐档」没有基线就没有前后对比，违反「优化必须前后对比」（§三 L4 纪律），升格无从验收。
  - 场景错配疑点：group commit 官方定位是**高并发小批量合并**（多 load 合一事务）；本仓 T6 批分布实测默认档批=16000 行/批（§4.6 `BENCHMARKS.md:305`）、字节档 8000 行——已是中大批量，恰在 group commit 收益区外。收益成立的场景（N 条管道 × 小批）在本仓**无并发多管道宏基准**。
  - 语义取舍未裁决：async_mode 返回即卸责（放弃 label 级确认），与现有「flush 成功=已提交」的游标推进判据（runtime :766-786）冲突，需要显式取舍矩阵。
- **触发条件**：T1=先立「Doris sink 宏基准」小卡（kafka→doris / file→doris，单管道+多管道并发档，~1.5 人日，产出即③④共同的门槛输入）；T2=该基线显示默认档吞吐不达标且瓶颈在 FE 事务/BE compaction 队列而非网络/CPU；T3=真实出现多管道小批量场景（≥4 管道 × <1000 行/批）。
- **任务卡草案要点**（触发后，估 ~2-3 业余人日）：datasource 级配置透传 `group_commit`（off/sync/async）；语义文档（async_mode 下游可见性与幂等锚的取舍矩阵入 docs/connectors/doris.md）；多管道并发宏基准入 BENCHMARKS（§六第二机口径）。

## ⑦ S3/CDC 路线（设计 §7.4 P2 序 #4）+ jdbc live-gate 形态裁决

### ⑦a S3/CDC 路线 —— 结论：排 v1.x（CDC 优先走「Debezium JSON decode 格式」廉价路径；S3 押后到①升格后）

- **现状证据**：`engine/crates/tailrace-conn-s3/src/lib.rs` = 1 行占位（同⑥）；decode 现有实现 4 个（json/csv/ogg/parquet，BENCHMARKS §4.5 :233 记「全部 4 个实现是无状态 unit struct」），grep `debezium|canal|maxwell` **0 命中**；README :51 S3 占位行。
- **门槛数据**：
  - CDC 廉价路径成立：Debezium→Kafka 是标准部署，engine 侧只需一个新 Decoder 格式（debezium JSON envelope 与现有 OGG envelope 同构：payload/before/after/op 结构），conn-kafka/runtime **零改动**（T4/T13 先例：新格式/新连接器不动本体）。成本 ~1.5 人日 vs 直连 binlog/逻辑复制（重连接器 + 红线风险）。
  - S3 反例数据：T16 刚把「裁剪 −5.52 MiB/−9.4%」立为轻量支柱的数字（§6.2 `BENCHMARKS.md:482-491`）；S3=object_store/aws 栈会把体积显著加回，与支柱 1 相抵；且 S3 无需求信号（共同事实 1）。若①deltalake 升格（其自身带 object_store ^0.13.2），S3 source 的依赖边际成本才降为零。
